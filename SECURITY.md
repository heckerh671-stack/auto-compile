# Zalard — anti-tamper notes

Honest framing first: everything here runs on the attacker's machine, so none of it is unbreakable.
A determined person with IDA/x64dbg and time beats all of it. The goal is to raise the bar so casual
crackers and leakers give up, and to stop drop-in tampering. The native port (all logic in the DLL)
is the big win; the items below harden it further.

## What's implemented

1. **String obfuscation in the DLL** (`native/logic/obf.h`).
   Sensitive literals are wrapped in `XS("...")`. The characters pass through a user-defined literal
   as template parameters, are stored XOR'd, and are decrypted at runtime through a *volatile* read
   (so the compiler can't fold them back to plaintext). `strings zalard_gui.dll` no longer shows item
   IDs (`minecraft:...`), file names (`config.json`, `friends.txt`), the bridge class name, or the
   JNI method/signature strings.
   - **The feature map is hidden too.** Every module name ("Aim Assist", "Crystal", "Ping Spoof"…),
     every setting name ("Reach", "Silent Auto Hit", "Spoof Name"…), the category labels, the combat
     enum options ("Camera/Silent", "Crosshair/Closest", "W-Tap/S-Tap"…) and the old-name→new-name
     config-migration table are all `XS`-wrapped. `strings` on the decrypted DLL shows none of them.
     To make that safe, the GUI model *copies* each name into its own string pool when a module or
     setting registers (`newModule`/`newSetting` call `intern()`), and `sEnum` interns its options —
     so the pointer the model keeps never points at the short-lived decrypt buffer. (A runtime test,
     `registerModules()` then printing every name, confirms all 20 modules / 174 settings / enum
     options still come out correct.) The only on-screen strings deliberately left plaintext are
     generic UI chrome ("configs", "friends") and the vanilla Minecraft cape list in the cape spoofer
     — neither says anything about what the client does.
   - **Ephemeral decrypt (anti-dump).** For *transient* strings (item IDs, file names, JNI names used
     once), `XS` doesn't decrypt into a static buffer that then sits in memory for the rest of the
     run. It decrypts into a small 64-slot ring that is overwritten as it's reused, so such a string's
     plaintext only exists for the moment it's needed and a later RAM dump catches a mostly-empty ring
     instead of a tidy table. (Names that have to persist to be drawn do live in the pool for the
     session — see "does NOT do" below. The win for those is hiding them from *static* analysis of the
     DLL file, not from a live-memory dump.)

2. **Hidden JNI exports** (`native/logic/jni_table.h`, generated by `tools/gen_jni.py`).
   The DLL used to export 64 `Java_dev_zalard_nat_Z_tick`-style symbols — a labelled map of the whole
   API. Now the native methods are bound with `RegisterNatives` from a single `JNI_OnLoad`, and their
   names are `XS`-encrypted. The export table shows only `JNI_OnLoad`.

3. **Jar ↔ DLL binding** (`tools/gen_guard.py`, `tools/seal.py`).
   - A random 128-bit **token** is baked into both the DLL (`native/logic/guard_token.h`) and the jar
     (`dev.zalard.nat.Z.TOKEN_HI/LO`). `boot()` refuses to start the logic unless they match, so a DLL
     and a jar from different builds — or a swapped/patched DLL — won't run together.
   - The jar also pins the **SHA-256** of the exact native library it ships with, per OS
     (`ZalardNative.DLL_SHA256` / `SO_SHA256` / `DYLIB_SHA256`, filled by `seal.py`); the decrypted
     payload is checked against the pin for the running OS on **both** load paths — the native-decrypt
     stub and the Java fallback — so a replaced or tampered library is refused at load on every platform,
     and forcing the fallback can't slip a modified payload past the check. On an unsealed dev build the
     pin is `""` and the check is skipped.

4. **Anti-debug** (`native/logic/obf.h`).
   Reads the Windows PEB directly (no imports): `BeingDebugged` and `NtGlobalFlag`. Checked at boot
   and periodically; on a hit the logic quietly winds down after a randomized delay, rather than
   crashing next to the check (harder to locate, fewer false-positive crashes).

5. **Encrypted DLL inside the jar** (`tools/seal.py`, `ZalardNative.java`).
   The jar does not carry a usable `zalard_gui.dll` at all. `seal.py` encrypts the built DLL to
   `/natives/zalard_gui.bin` with a SHA-256 keystream cipher under a per-release key, and deletes the
   plaintext `.dll`. At load, `ZalardNative` reads the `.bin` and hands the ciphertext to the native
   decrypt stub (`zalard_loader`), which assembles the plaintext in **native** memory, verifies it
   against the pinned per-OS SHA-256 there, and writes it straight to a throwaway temp file with a
   nondescript name (`deleteOnExit`) — the plaintext library never becomes a `byte[]` on the JVM heap, so
   a heap dump can't lift it. A **sealed** build (encrypted payload with a per-OS hash pinned in) is
   **fail-closed**: if the stub is unavailable or fails, `ZalardNative` refuses to start rather than
   decrypt in Java — so an attacker can't delete or block the stub to force an in-heap decrypt and open a
   heap-dump window at the plaintext (and a stub that rejects a tampered payload likewise stops startup).
   Only an **unsealed dev build** (plain lib, or no pin for this OS) decrypts in Java, where there's no
   pinned secret to expose. So unzipping the
   jar hands a leaker only ciphertext — `strings zalard_gui.bin` shows nothing, not even the PE
   `"This program cannot be run in DOS mode"` stub. (The decrypted DLL still has to exist as a temp
   file while Windows loads it; that's inherent to `System.load`. The win is that the *distributed*
   artifact is opaque.)

6. **Instrumentation-agent hardening** (`ZalardNative.antiAgent`).
   The classic "attach and dump every loaded class / byte array" uses a `-javaagent` / `-agentlib` /
   `-agentpath` JVM agent. `ZalardNative` inspects its own JVM input arguments at load and refuses to
   run if one is present. Pair it with `-XX:+DisableAttachMechanism` in the launcher to also block
   external `jcmd`/`jmap` attach after startup.

7. **Virtualized guard** (`native/logic/vm.h`).
   The protection-critical check — *does the jar's token match, and is a debugger attached?* — is not
   compiled as a plain `cmp`/`jz` a cracker can find and NOP. It's hand-assembled into bytecode for a
   tiny stack VM and run by an interpreter; the bytecode itself is stored XOR-packed and decoded
   through a volatile read right before it runs. To defeat it you first have to reverse the VM and its
   program, not just flip one branch. (This virtualizes the guard only — virtualizing the whole client
   would be enormous and far too slow. It raises the bar, like everything else here.)

The GUI typeface is also Zalard's own (`tools/zfont.py`): original hand-drawn pixel bitmaps, so the
client ships no third-party font and there's no OFL/asset attribution to carry.

### Rebuilding (order matters)

```
python3 tools/gen_guard.py      # new token (DLL header + Z.java) AND new encrypt key (ZalardNative)  [per release]
python3 tools/gen_jni.py        # regenerate the JNI table if native methods changed
python3 tools/gen_atlas.py native/font_atlas.h atlas.png    # only if the font (tools/zfont.py) changed
sh tools/build_dll.sh           # build zalard_gui.dll with the token + atlas baked in
python3 tools/seal.py           # sha256 -> ZalardNative, encrypt DLL -> zalard_gui.bin, delete plaintext .dll
# then build the jar (build-zalard.bat)
```

Order matters: `gen_guard` must run before `build_dll` (the token is compiled in), and `seal` must run
after (it hashes and encrypts the finished DLL). `gen_atlas` needs `msdfgen` on `PATH` or `MSDFGEN=`;
skip it unless you changed the font. If you skip `gen_guard`/`seal`, the token is all-zero, the hash
check is empty, and the jar falls back to a plaintext `/natives/zalard_gui.dll` — the client still runs
(handy while developing), it just isn't bound or encrypted. Run the full sequence for a real release.

### What this does NOT do

- It does not help against server anti-cheats (Grim etc.). Hiding your code and evading detection are
  different problems; nothing here touches the latter.
- It does not stop someone who rebuilds both halves from source (they have the source).
- The jar is still partly readable (Fabric entrypoint, mixins, the bridge). That's unavoidable —
  Fabric only loads Java, and mixins must be Java. The bridge documents the native API surface but
  not the logic.
- It does not make a *running* process secret-free. The DLL has to be decrypted to be loaded, and the
  names have to be in a readable pool to be drawn, so a full **RAM dump of the live process** still
  yields the decrypted code and the on-screen names out of the pool. Note the difference from static
  analysis, though: grabbing the temp `.dll` file and running `strings` on it no longer reveals the
  feature map — those names live XOR-encoded in `.rdata` and only materialize in the pool once the
  process is running. So the bar is now "attach a debugger / dump live memory", not "unzip and grep".
  The ephemeral ring, the agent block and `DisableAttachMechanism` make the live-dump route harder and
  messier, not impossible. What is fully protected is the *distributed* jar: it carries only ciphertext.

## Stopping leaks of a built client (licensing / activation)

This is a different goal from code theft, and it genuinely conflicts with the current "build it
yourself" model: if each user compiles their own jar, there is no single binary to license. To do
leak-prevention you'd ship **built** jars (not source) and add an activation layer. A realistic
design:

**Keys + online activation (recommended)**
- You run a small license server (any cheap host). It holds issued keys and their state.
- Each user gets a key. On launch, the client POSTs `{key, hwid, nonce}` over HTTPS; the server
  checks the key is valid and not already bound to a different machine, binds it on first use, and
  replies with a signed token (Ed25519) containing `{hwid, expiry}`.
- The DLL holds the server's **public** key only, verifies the signature, checks `hwid` matches this
  machine and `expiry` is in the future, and refuses to boot otherwise. Because the DLL only verifies
  (never signs), a cracker can't mint tokens without the server's private key — they have to patch the
  check out of the DLL instead, which is the usual cat-and-mouse but far above casual leaking.
- **HWID**: hash a couple of stable machine traits (e.g. volume serial + CPU brand). Keep it coarse so
  users don't get locked out by minor hardware changes; let the server re-bind on request.
- **Offline grace**: cache the last signed token and allow N days offline so a server blip doesn't
  brick everyone.
- Revocation is just flipping the key's state server-side; the next activation fails.

**HWID-only (no server)**
- Simpler: bake a per-user allowlist of HWIDs into their build, DLL refuses other machines. No server,
  but no revocation and you must rebuild to add users. Fine for a handful of trusted people.

**Watermarking (catch the leaker)**
- Stamp each build with an invisible per-user ID (in the DLL token and a hidden Java constant). If a
  build leaks, you can tell whose it was. Cheap, and a real deterrent for a small circle.

Honest limits: activation stops *sharing the file*, not a determined reverser who patches the check.
Combined with the obfuscation above it's enough to keep a paid/private client out of casual hands.
